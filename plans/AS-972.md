## 1. What exists today (verified in `/root/LibreClinica`, `lc-develop` @ `8399fea3d`)

Already working: `POST /auth/api/v1/studies`, `POST /studies/{id}/sites`,
`POST /studies/{id}/eventdefinitions`, clinical-data read, discrepancy notes,
user creation, system config, ODM metadata **export**, SOAP endpoints.

Missing (the four gaps this ticket fills):

1. CRF / version / item / item-group / response-set creation via the v1 REST API.
2. ODM `Study` metadata import (export exists; import parses `ClinicalData` only).
3. Arms (`StudyGroupClass`) creation via API.
4. Instrument↔event designation (`EventDefinitionCrf`) via API.

### 1.1 Critical implementation finding

**Do not reuse `CreateCRFVersionServlet` or `SpreadSheetItemUtil`.** The servlet
is tied to `HttpServletRequest`/session/`forwardPage`, and its writes go through
`NewCRFBean.insertToDB()` with raw SQL generated during Excel parsing.
`SpreadSheetItemUtil` is a 718-line validator/DTO — no creation logic.

The correct template is **`XformMetaDataService.createCRFMetaData()`**
(`core/src/main/java/org/akaza/openclinica/service/crfdata/XformMetaDataService.java:136`):
a `@Service`, `@Transactional` method with injected DAOs and no servlet
dependency. `plans/AS-958-libreclinica.md` §4 still names the servlets — that
note is stale and will be corrected when this work starts.

### 1.2 Wiring facts (no new config required)

- Controllers: `web/src/main/java/org/akaza/openclinica/controller/`, classic
  `@Controller` + `@RequestMapping`, e.g. `StudyController.java:55-57,142`.
- Discovery: `web/src/main/webapp/WEB-INF/pages-servlet.xml:24` component-scans
  `org.akaza.openclinica.controller`; Jackson converter at `:62-64,71-74`.
- URL: `pages` DispatcherServlet maps `/pages/*` (`web.xml:191-199`), so
  `/auth/api/v1/foo` is reachable at `/LibreClinica/pages/auth/api/v1/foo`.
- Auth: `apiSecurityFilter` on `/pages/auth/api/*` (`web.xml:177-187`) applies
  automatically to any new controller under that prefix.
- DTOs: plain POJOs in a new `core/.../bean/crf/` package, mirroring
  `bean/login/StudyDTO`.

## 2. Phase 1 — CRF creation endpoint (first PR, ~3–5 days)

### 2.1 Authorization and ownership

- `ApiSecurityFilter` authenticates the API key to a `UserAccountBean` and stores
  it at `request.getSession().getAttribute("userBean")` (`ApiSecurityFilter.java:86`).
- `CrfController` takes `HttpServletRequest`, reads `userBean`, and refuses unless
  the account is a global admin: `isTechAdmin() || isSysAdmin()`
  (`UserAccountBean.java:353-366`), matching `StudyController.getStudyOwnerAccount`
  (`StudyController.java:1023-1029`).
- This is **admin auth** (global user type), not a study role and not participant
  auth. Study-scoped authz is deferred to a later hardening ticket.
- Every entity create needs an owner; pass the resolved `UserAccountBean` through
  to the service and set it on each created bean.

### 2.2 Study resolution

- The path is `/auth/api/v1/crfs/{studyOid}`; resolve `{studyOid}` with the classic
  `StudyDAO.findByOid(oid)` (`core/.../dao/managestudy/StudyDAO.java:415`). The
  Hibernate `StudyDao` has no `findByOid` (only `domainClass()`). Return a
  validation-failed response if the study is missing.

1. **DTOs** `core/src/main/java/org/akaza/openclinica/bean/crf/`
   - `CrfCreateRequest`: crfName, description, versionName, revisionNotes,
     items[] (name, label, type, choices, required, section), groups[],
     optional eventOid.
   - `CrfCreateResponse`: crfOid, crfVersionOid, created ids.
2. **Service** `core/src/main/java/org/akaza/openclinica/service/crfdata/CrfMetadataCreationService.java`
   - `@Service`, `@Transactional createCrf(...)`.
   - Reuse the create order and OID/status/type-resolution logic from
     `XformMetaDataService:141-198,232-347`:
     `CrfDao` → `CrfVersionDao` → `SectionDao` → `ItemGroupDao` → `ItemDao` →
     `ResponseSetDao` → `ItemFormMetadataDao` → `ItemGroupMetadataDao` →
     `VersioningMap`, plus `EventDefinitionCrfDao` when eventOid is supplied.
   - Response sets: no classic `ResponseSetDAO.create` and no option table.
     `ResponseSet` stores choices denormalized as `optionsText`/`optionsValues`
     (comma-separated; `domain/datamap/ResponseSet.java:45-46`, columns length
     4000). Build those strings directly from our `code, label` pairs and
     `ResponseSetDao.saveOrUpdate`; use `ResponseSetDao.findByLabelVersion` for
     idempotency. Do **not** reuse `ResponseSetService` — it derives options from
     Xform `Html` parsing and is not JSON-friendly. Flag the 4000-char cap for
     large code lists.
3. **Controller** `web/src/main/java/org/akaza/openclinica/controller/CrfController.java`
   - `@RequestMapping("/auth/api/v1/crfs")`, `POST /{studyOid}` with `@RequestBody`,
     returning `ResponseEntity<Object>`. Follow `StudyController`'s
     `ClassCastHelper` / `HashMap` style if typed binding is awkward.
   - Enforce §2.1 (admin) and resolve the study per §2.2 before delegating to the
     service.
4. **Tests**
   - Service: `core/src/test/java/.../service/crfdata/CrfMetadataCreationServiceTest.java`
     — JUnit 4 + `MockitoJUnitRunner` (Mockito 1.9.5), mock each DAO, verify call
     order, OID assignment and status. Template: `TwoFactorServiceTest.java`.
   - Controller authz: add `spring-test` (MockMvc) — no precedent in this repo
     yet, so add the dependency. Test that a non-admin `userBean` is refused and a
     TechAdmin/SysAdmin is accepted (covers §2.1).
5. **Verify**
   - `mvn -q clean install -DskipTests=false` — tests are **skipped by default**
     (`pom.xml:24`, surefire `:895-902`).
   - POST to `/LibreClinica/pages/auth/api/v1/crfs/{studyOid}` with the API key and
     a minimal CRF payload; confirm via `/rest/metadata/xml/view/{oid}`.

### Build gotchas

## 3. Phase 2 — ODM Study import, self-contained (next PR, ~5–10 days)

- One endpoint accepts the ODM XML emitted by `make libre-odm` and creates the
  whole graph in one transaction: events, forms, item groups, items, response
  sets, and event↔form designations (absorbing gap 4).
- **Input:** ODM XML (request body). **Output:** JSON matching the existing
  `{"message":"SUCCESS"/"VALIDATION FAILED", ...}` envelope — never XML.
- Unmarshal via the existing `jaxbMarshaller` (`pages-servlet.xml:52`, context
  path `org.cdisc.ns.odm.v130`, `org.cdisc.ns.odm.v130_api`, OpenClinica ext
  v130).
- Map `StudyEventDef` → event definition (reuse the `EventDefinitionDTO` builder
  from `StudyController.createEventDefinition`), `FormDef` → CRF, `ItemDef` →
  item, `CodeList` → response set, `FormRef` → `EventDefinitionCrf`. **No
  ODM→entity mapper exists** — net-new mapping, reusing Phase 1's creation
  service for the CRF/item half.
- Idempotency / CrfVersion strategy: match by OID → update in place (else
  create). Safe while studies are empty; once real data is collected, follow the
  "freeze before data" rule from §6.
- Tests: unmarshal a fixture ODM (from `make libre-odm`), assert the DTO list and
  DAO calls; add an idempotency test (import twice → no duplicates).

## 6. Decisions

1. **CrfVersion strategy (decided):** match by OID → update in place, else create.
   Freeze field/form names before real data collection (same rule as REDCap);
   after freeze, treat renaming as destructive and version instead.
 2. **Authz (revised 2026-11-23):** allow a global SYSADMIN/TECHADMIN API key **or**
    a `STUDYDIRECTOR`/`COORDINATOR` role on the target study (the upstream
    `getSiteOwnerAccount` pattern). The original global-admin-only rule blocked the
    live sandbox, where the API key's user is a global `USER` with a `director` role
    on the study — a study-scoped design import legitimately needs only study-level
    authority. Unit tests cover admin / director / coordinator accepted and
    no-role / data-entry / no-user refused.

3. **Dual auth (open)** — keep UI credentials in `.env.libre` for
   `/rest/metadata/*`, or add a metadata endpoint behind the API-key filter and
   drop the password? (Consumer decision in this repo.)
4. **Upstream scope (open)** — will ReliaTec accept an ODM Study-import feature?
   Confirm on the issue before writing Phase 2.
5. **Scratch study (open)** — permission to create one on the live LC sandbox to
   exercise `import_events` / the new endpoints end-to-end.

### 8.1 Consumer-repo follow-up (arx-redcap-xprize-trial)

The Python ODM emitter (`src/arx_trial/odm.py`) is not standards-compliant, so the
ODM import silently drops data. Verified against the ODM 1.3 JAXB classes, it must:

1. emit `StudyEventDef` instead of `EventDef` (MetaDataVersion/StudyEventDef);
2. emit `FormRef FormOID="..."` instead of `FormRef OID="..."`;
3. move `CodeList` from inside `ItemDef` to MetaDataVersion level, referencing it
   from `ItemDef` via `CodeListRef CodeListOID="..."`;
4. use `Mandatory="Yes"/"No"` on `ItemRef` (YesOrNo) instead of `"O"/"R"` (and drop
   the non-standard `Mandatory` on `ItemDef`).

The emitter's own parser (`parse_metadata`/`parse_events`) and the round-trip test
must be updated to match, then `LibreClinicaTransport.import_metadata` should POST
the emitted ODM to `/auth/api/v1/odm/studies/{studyOid}` instead of raising the gap
error, and `import_events`/`import_instrument_event_mappings` should follow the
ODM import path. `make libre-odm-check` must still pass.

### 8.2 End-to-end test findings (2026-11-23)

Live e2e (`make libre-e2e` in the consumer repo) exposed three issues, in order:

1. **415 Unsupported Media Type** — `pages-servlet.xml` has no
   `StringHttpMessageConverter`, so `@RequestBody String` cannot read
   `application/xml`. Worked around client-side: the consumer now sends the ODM as
   a JSON string with `Content-Type: application/json` (Jackson deserializes it to
   String). Proper server fix (add `StringHttpMessageConverter` to the adapter's
   converter list) is still pending.
2. **403 Forbidden** — the API key's user is a global `USER` with a `director` role
   on the study; the original global-admin-only check rejected it. Fixed by §6.2
   (global admin **or** study director/coordinator).
3. **JAXB SAX failure** — the WAR bundles `xercesImpl-2.6.2` / `xml-apis-1.3.04`,
   whose `SAXParserFactoryImpl` rejects the `secure-processing` feature JAXB tries
   to set:
   `SAXNotRecognizedException: Feature 'http://javax.xml.XMLConstants/feature/secure-processing'`.
   **Fix:** `OdmStudyImportService` now parses the XML into a DOM `Document` and
   calls `unmarshaller.unmarshal(Document)` (the JAXB DOM path does not create a
   SAX parser). Verified against the actual WAR classpath: `StringReader` fails
   with the exact deployed error, DOM unmarshal succeeds.
   Root-cause follow-up: remove/upgrade the ancient `xercesImpl` so JDK JAXP is used.
